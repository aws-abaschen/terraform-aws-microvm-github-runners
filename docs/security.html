SecurityThreat model and controls

What an attacker controls, what they can reach, and what stops them.

ThreatControl
Malicious job (PR author, compromised dependency) persists into later jobsOne Firecracker VM per job, terminated afterwards, no reuse (ADR-001). JIT runners accept exactly one job.
Job reads another repository's secretsThe runner role is limited to gha/<owner>/<repo>/* and capped by the per-repo boundary. Even a widened identity policy cannot exceed the boundary.
Job steals the GitHub App keyThe key is readable only by the broker role. The secret's resource policy denies everyone else, and every repo boundary explicitly denies it.
Repository deploy role escalates (new role, removed boundary)iam:CreateRole requires the repo's own boundary. Removing a boundary, creating policy versions, users or access keys is denied.
Repository asks the broker for another repository's tokenThe broker runs the presigned GetCallerIdentity itself (regional STS host only, no SSRF). It requires the role <prefix>-<sha256(repo)[:10]>-control in its own account and an onboarded repository, and scopes the token to that one repository.
Job kills other runnersThe runner role has no MicroVM permissions. The control role can only Get/Terminate VMs of its own image ARN.
JIT config replay or theftNever in the run payload. Stored as a KMS SecureString under a per-runner name, read and deleted by the VM in /run, and deleted again on cleanup.
Forged webhookConstant-time HMAC-SHA256 check, wrong repository rejected, 1 MB body cap. Optional AWS_IAM mode behind a central ingress with WAF.
Data exfiltration from a jobNo NAT in the account. All traffic goes through the central egress and its firewall allow-list. MicroVMs use NO_INGRESS; shell and auth tokens are denied by the boundary.
Supply chain (runner, Lambda code, actions)Runner tarball SHA-256 pinned, reproducible builds, SLSA build provenance and SBOM on every release, consumers verify with gh attestation verify, optional Lambda code signing, every action pinned by commit SHA.
Secrets in Terraform stateThe webhook secret is ephemeral and written with secret_string_wo. The App key is set out of band. State is encrypted with KMS and versioned.

Rule for workflow authors: the runner role is available to every job, including pull requests from anyone with write access. Keep only CI-grade secrets under gha/<owner>/<repo>/. For deployments use GitHub OIDC with roles whose trust is bound to a protected Environment (repo:<owner>/<repo>:environment:production).

Hardening checklistBefore production

  • Use private or internal repositories. For public ones, require approval for all outside contributors and never use pull_request_target on these runners.
  • Restrict the central egress firewall to GitHub, your package registries and AWS endpoints.
  • Prefer webhook_auth_type = "AWS_IAM" behind a central API Gateway with WAF if your SCPs forbid public Function URLs.
  • Enable Lambda code signing (code_signing_config_arn) and sign lambda.zip with AWS Signer.
  • Set an organisation permissions boundary on the platform roles (permissions_boundary_arn).
  • Rotate the webhook secret by bumping webhook_secret_version. Rotate the GitHub App key yearly in GitHub, then update the secret.
  • Install the GitHub App only on onboarded repositories.
