IAM designPolicies and guardrails that scale with the number of repositories

Design rule: nothing in IAM policies, SCPs, RCPs, key policies or platform configuration grows with the number of repositories. A repository costs a fixed set of roles and resources. Once an account's quotas are reached, you add another account (a cell), not a bigger policy.

Phase 1 implemented · 2026-11-21

Status: phases 1 and 2 are implemented. The boundary is 6,028 characters whatever the number of repositories. IAM Access Analyzer validates the boundary, the SCP, the RCP and both new trust policies with no findings (the entry role gets the expected wildcard sub warning). 60 SimulateCustomPolicy cases confirm that repository A gets its own resources and is denied B's and the platform's, through its own deploy role or the shared one, including when a role named for B carries A's tags. Further simulations cover the SCP: only the tagger can set gha-* session tags, and only administrators can change the platform roles. In the sandbox (2026-11-21), the smoke test passed 6 of 6: the tagger fetched the GitHub JWKS through the egress path and refused a forged token, and a MicroVM ran with the tag-scoped runner role. Not yet run for real: a GitHub workflow through either deploy path (including CreateMicrovmImage with tags), the broker's registry lookup, and the SCP and RCP attached to an OU.

RecommendationPrincipal-tag ABAC, with the tag used inside resource ARNs

Every repository principal carries two tags: gha-repo-id (sha256(lower(owner/repo))[:10]) and gha-repo (owner/repo in lower case). The generic policy grants permissions on ARNs built from those tags with policy variables:

arn:aws:lambda:<region>:<account>:function:gha-microvm-${aws:PrincipalTag/gha-repo-id}-*
arn:aws:ssm:<region>:<account>:parameter/gha-microvm/${aws:PrincipalTag/gha-repo-id}/*
arn:aws:secretsmanager:<region>:<account>:secret:gha/${aws:PrincipalTag/gha-repo}/*
arn:aws:s3:::gha-microvm-artifacts-<account>-<region>/${aws:PrincipalTag/gha-repo-id}/*

Why this rather than plain resource-tag ABAC (aws:ResourceTag equal to aws:PrincipalTag on every statement):

  • It works for every action that has a resource ARN. Some actions here have no aws:ResourceTag condition key, such as log stream writes, S3 objects and parts of the new Lambda MicroVMs API. A resource ARN always works.
  • Names can't change, tags can. Anyone allowed to tag a resource could otherwise move it into another repository. With names, a tag change on a resource grants nothing.
  • Creates work too. The name in the request is checked before the resource exists, with no dependence on tag-on-create support.
  • It doesn't care where the tag comes from. A role tag and a session tag are both aws:PrincipalTag. The policy is the same in phase 1 and phase 2.

Resource tags are still used for three things:

  • creates whose resource is * (lambda:CreateMicrovmImage): aws:RequestTag/gha-repo-id must equal the caller's tag. Network interfaces stay unscoped, because Lambda creates them and their requests carry no tag.
  • opt-in sharing: a secret or parameter tagged gha-repo-id=<id> becomes readable by that repository's jobs, without any policy change
  • a second layer in the RCP, described below

IdentitiesWhere the tags come from

Phase 1: role tags

bootstrap creates one deploy role per repository, trusted by GitHub OIDC for repo:<owner>/<repo>:environment:<env> and tagged with both keys. All other repository roles are created by that deploy role. The policy only allows iam:CreateRole when the request carries the caller's own gha-repo-id and gha-repo values and the generic boundary. A repository can therefore only create roles of its own.

Phase 2: the tagger, with session tags

A role with session tags lets one shared deploy role serve every repository. GitHub can't provide this on its own. AssumeRoleWithWebIdentity takes session tags only from a https://aws.amazon.com/tags claim in the JWT, and GitHub's OIDC tokens don't include it. A small platform function, the tagger, does it instead. Enable it with bootstrap.tagger_github_owners; the example workflow is examples/consumer-repo/.github/workflows/deploy-runners-tagger.yml.

  1. The deploy workflow assumes the shared entry role <prefix>-deploy-entry through OIDC. Its trust is repo:<owner>/*:environment:*, one line per allowed GitHub owner. It relies on the default sub format: an organization with a customized sub must adapt it. The entry role can only invoke the tagger.
  2. The workflow sends a second GitHub OIDC token, with audience <prefix>-tagger. The tagger accepts RS256 only, with a key from the issuer's JWKS (cached one hour, refreshed at most once a minute for an unknown kid). It checks the issuer and the audience exactly, and exp, nbf and iat with one minute of clock skew. It never reads sub: the repository and environment come from the repository, repository_owner and environment claims.
  3. The owner must be allowed, the registry entry must exist for the full repository name, and the token's environment must equal the entry's. A reused jti is refused (DynamoDB conditional write with a TTL, KMS encrypted, point-in-time recovery).
  4. The tagger calls sts:AssumeRole on <prefix>-deploy with session tags gha-repo-id and gha-repo, SourceIdentity=<owner>+<repo>@<run_id> for CloudTrail, and at most one hour (role chaining). It returns the credentials and never logs them.
  5. The shared deploy role trusts only the tagger, requires both tags and no other keys, and has no gha-* role tags. The boundary's TagMatchesName statement accepts its exact ARN, not a deploy* pattern. The SCP denies sts:TagSession with either key to every principal except the tagger, and protects <prefix>-deploy* and <prefix>-tagger*.

With phase 2, onboarding a repository only means writing its registry parameter. The per-repository deploy roles stay until per_repository_deploy_roles = false, so both paths can run side by side during a migration.

Organization guardrailsSCP, RCP and tag policy (module org-guardrails)

Every policy is generic: it holds only the name prefix and a list of exempt administrator roles. It is the same for every account and every number of repositories. The platform team attaches it to the workload OU from the management account or a delegated administrator.

SCP: makes the tags trustworthy

  • DenyForeignRepoTags. A request that sets or removes gha-repo-id or gha-repo on any resource or principal is denied unless the value equals the caller's own tag. This covers create-with-tags, TagResource, TagRole and every Untag*. Exempt administrators are excluded. Without this rule, anyone who can tag could pass for a repository.
  • DenyRepoSessionTags. sts:TagSession with a gha-repo-id tag is denied to everyone but the tagger role.
  • DenyBoundaryEscape. Principals tagged gha-repo-id can only create roles, or set a boundary, with <prefix>-boundary. They can't delete a boundary, create policy versions, users or access keys.
  • ProtectPlatform. Only exempt administrators can change the boundary policy and the platform roles: broker, deploy, tagger and connector operator.
  • DenyMicrovmShell. MicroVM shell and auth tokens are denied across the organization, except for a break-glass role.

RCP: second layer on data

The RCP denies access to resources tagged gha-repo-id when the caller carries a different gha-repo-id. It covers Secrets Manager, SQS, DynamoDB, CloudWatch Logs, CloudWatch and X-Ray, the RCP-supported services used here. Callers with no gha-repo-id tag are left out (Null check), so administrators and AWS services are unaffected. A job's extra identity policy (additional_runner_policy_json), even one granting *, then still can't read another repository's secrets or queues.

Tag policy

Fixes the spelling and case of gha-repo-id and gha-repo and reports resources that don't comply. Tag policies can't require a tag or check a value against a pattern. The SCP does both.

Limits to know

  • SCPs and RCPs don't apply to the management account or to service-linked roles.
  • A deny on StringNotEquals also matches a caller that lacks the key. That is why each SCP rule has the list of exempt administrator roles (for example the AWS SSO administrator roles and the platform pipeline role).
  • For actions without aws:ResourceTag, the RCP doesn't apply. The identity layer, built on names, is the primary control, and the RCP is only the second one.
  • SCPs and RCPs are limited to 5,120 characters each, with up to 5 per target. The guardrails use one of each.

Past one account, assign repositories to cells. Each cell is an account with its own bootstrap, and the same SCP and RCP apply to all of them. A repository's deploy workflow points at its cell's role. Nothing is shared between cells, so a failure stays inside one cell.

MigrationBreaking changes before v0.1.0

  • repositories[*].job_secret_prefixes, job_parameter_paths and additional_job_actions are removed. Use the gha/<owner>/<repo>/ paths or tag a secret or parameter with gha-repo-id. Use bootstrap.additional_job_actions for the whole account.
  • repo-runner loses job_secret_prefixes and job_parameter_paths, for the same reason.
  • The platform configuration has boundary_arn instead of boundaries. Run bootstrap first, then each repository.
  • The broker reads the registry instead of ALLOWED_REPOSITORIES.
