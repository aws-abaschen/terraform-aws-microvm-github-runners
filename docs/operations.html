DLQ: jobs could not be dispatched

  1. Look up the reason: Logs Insights on the dispatcher, filter msg = "dispatch failed".
  2. Common causes: quota (ServiceQuotaExceededException), image version inactive, broker refusing (see below), GitHub API outage.
  3. Fix the cause, then redrive: aws sqs start-message-move-task --source-arn <dlq_arn>. Jobs still queued at GitHub are also picked up by the sweeper.

Queue age: jobs wait more than 10 minutes

  1. Check ActiveRunners against max_runners. If saturated, raise max_runners or reduce parallel jobs.
  2. Check MicroVM memory quota usage in Service Quotas (running and suspended VMs count).
  3. Check the dispatcher for Throttled metrics and errors.

Lambda errors

  1. Open the function's log group and filter on level = "ERROR".
  2. VPC issues (timeouts to AWS APIs or GitHub) point to endpoint DNS or the central egress path. Test from the VPC with a Reachability Analyzer path to the TGW.
  3. Webhook 401: secret mismatch. Webhook 403: delivery for another repository.

Broker errors

  1. broker.denied audit events show the reason: repository not onboarded, wrong caller role, or a foreign account.
  2. read app secret errors: the App key secret is empty or malformed. It must be {"app_id": 123, "private_key": "-----BEGIN ..."}.
  3. GitHub 401: the App key was rotated or revoked; update the secret.

Dispatch errors

As for the DLQ. Each failure cleans up its JIT parameter and runner registration before retrying, so repeated errors do not leak runners.

Sweep errors

The sweeper needs the broker and GitHub. Check broker errors and GitHub status. While the sweeper fails, lost webhooks are not repaired, but normal dispatch still works.

Sweeper silent

The EventBridge Scheduler schedule gha-microvm-<id>-sweeper is disabled or its role cannot invoke the function. Re-apply the stack.

Reaped: a VM hit its hard lifetime

A job ran past max_job_minutes + 5. Make sure workflows set timeout-minutes to at most max_job_minutes. Check the job's runtime log for a hang.

Lost: VMs disappear before their job ends

Check StateReason with aws lambda-microvms get-microvm. Typical causes: out-of-memory (raise memory_mib), disk full (32 GB max at 8 GB baseline), or an AWS event. Jobs are re-dispatched.

ProceduresRoutine changes

Upgrade the runner

  1. Bump runner_version and both SHA-256 values in the justfile, and run just release-assets.
  2. Tag a release. Consumers bump RELEASE in their deploy workflow; the image builds a new version.
  3. Roll back by pinning image_version to the previous version.

Rotate secrets

  • Webhook: bump webhook_secret_version, apply, read the new value from Secrets Manager, update the GitHub webhook. The sweeper covers deliveries rejected in between.
  • GitHub App key: generate a new key in GitHub, put it in the App secret, delete the old key in GitHub.

Base image deprecation

AWS deprecates base image versions with 60 + 30 days notice. Bump base_image_version in runner-image and re-apply.

Emergency stop

  1. Disable the webhook in GitHub, or set reserved concurrency of the dispatcher to 0.
  2. Terminate running VMs: aws lambda-microvms list-microvms --image-identifier <image>, then terminate-microvm for each.
  3. Switch workflows to GitHub-hosted runners.
