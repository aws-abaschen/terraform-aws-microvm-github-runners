Ephemeral GitHub runners on
AWS Lambda MicroVMs

Each repository deploys its own runners into its own AWS account with Terraform. Every job gets a fresh Firecracker VM in your VPC, runs for at most one hour, can read only that repository's secrets, and is then destroyed. Built for landing zones without NAT, with central egress and VPC endpoints.

01 · DecisionsWhat we built and why

Runners only, jobs of at most one hour, enterprise landing zone, DORA in scope.

Lambda MicroVMs, one job per VM

A fresh Firecracker VM per job, per-second billing and no idle cost. The one-hour cap is well inside the 8-hour MicroVM limit.

Everything inside your VPC

Lambdas and MicroVMs use your private subnets. MicroVMs attach through a VPC_EGRESS connector, never INTERNET_EGRESS. Traffic follows the Transit Gateway to central egress and inspection.

Platform-owned token broker

Only the broker reads the GitHub App key. A repository proves its IAM identity with a presigned STS call and gets a one-hour token for its own repository only.

Per-repo IAM boundary

Each repository's deploy role, and every role it creates, is capped by a boundary tied to gha-microvm-<repo-id>-*. Repos sharing an account cannot touch each other.

Per-repo MicroVM image

Get/TerminateMicrovm are scoped to an image ARN. One image per repo means a dispatcher can only kill its own VMs.

arm64 by default, x64 available

Base image version 3 adds X86_64. Graviton is the cheaper default; pick x64 per repo when toolchains need it.

Public webhook, HMAC-verified

GitHub cannot sign SigV4, so the Function URL is public with HMAC checks by default. Set webhook_auth_type = "AWS_IAM" to accept calls only from a central ingress with WAF.

Ambient role is for CI secrets only

Every job, including pull requests, gets the runner role. Production credentials come from GitHub OIDC bound to protected Environments.

02 · ArchitectureThree modules, two accounts

The platform team applies bootstrap once per account and Region. Each repository applies runner-image and repo-runner from its own workflow.

ModuleApplied byCreates
bootstrapPlatform team, once per account and RegionKMS key, artifact and state buckets, runner security group, VPC_EGRESS connector, optional local endpoints, GitHub OIDC provider, per-repo boundary and deploy role, token broker, App key secret, alarm topic, platform config parameter
runner-imageRepository workflowImage artifact upload, build role, MicroVM image (arm64 or x64, Docker on)
repo-runnerRepository workflowWebhook, queue + DLQ, dispatcher, sweeper, state table, runner role, webhook secret (write-only), alarms

03 · Job lifecycleFrom queued to terminated

FailureHandling
Duplicate webhook deliveryA DynamoDB conditional claim on the job id drops the second launch.
Lost webhookThe sweeper lists queued jobs and re-queues those waiting more than 2 minutes. Stale claims (older than 5 minutes) are re-dispatched with a new attempt number.
Runner took another job (same labels)VMs are tracked by runner name, so completed always terminates the right VM. The left-over job is re-dispatched by the sweeper.
completed webhook lostGitHub removes a JIT runner after its job. The sweeper sees the runner gone and terminates the VM.
Capacity or quota reachedThe claim is released and SQS retries for about an hour. The queue-age alarm fires after 10 minutes.
RunMicrovm failsThe JIT parameter and runner registration are deleted, the claim is released and the message is retried. It lands in the DLQ after 20 attempts.
Job hangsGitHub cancels at timeout-minutes. Lambda kills the VM at 65 minutes, and the reaped alarm fires.

04 · Repo isolationRepositories sharing an account stay apart

Details are on the security page.

ADR-001Terminate after every job, no VM reuse

Keeping a finished VM idle so the next job starts faster saves little time and breaks the guarantee that every job gets a clean VM.

OptionStart timeIsolationIdle costVerdict
Reuse a running VMFastest✗ inherits the previous job's stateFull computeRejected
Suspend after the job, resume for the next oneFast✗ same dirty stateSnapshot storage, uses memory quotaRejected
Fresh VM per job, terminate afterSnapshot start + registration✓ clean every timeNoneChosen
Warm pool of clean, never-registered VMsSlightly faster✓ still one job per VMSnapshot storage, uses memory quotaOnly if measurements show a real gap

RunMicrovm already starts from a memory snapshot. Most of the remaining delay is registration and GitHub assigning the job, and reuse removes neither.

  image_arn       = module.image.image_arn
  image_version   = module.image.image_version
  architecture    = module.image.architecture
  max_job_minutes = 60        # VM hard limit = 65 min
  max_runners     = 5

}

Everything else (subnets, security group, connector, KMS key, broker, boundary) is read from the /gha-microvm/platform/config parameter written by bootstrap.

06 · OnboardingFrom zero to a first job

  1. Platform, once per account: apply bootstrap with the VPC, subnets and the list of repositories. Put {"app_id":…,"private_key":"…"} into the github_app_secret_arn secret out of band.
  2. GitHub App: grant repository permissions Administration: write and Actions: read, install it only on onboarded repositories.
  3. Repository: create the runners Environment (required reviewers, main only), and set the variables RUNNERS_DEPLOY_ROLE_ARN, RUNNERS_STATE_BUCKET and RUNNERS_STATE_KEY from the bootstrap outputs.
  4. Deploy: copy examples/consumer-repo. The workflow verifies release checksums and attestations, plans, archives the plan and applies it.
  5. Webhook: add a repository webhook to webhook_url with content type JSON, only the Workflow jobs event, and the secret from webhook_secret_arn.
  6. Use it: runs-on: [self-hosted, linux, arm64, microvm] and timeout-minutes: 60.
# .github/workflows/ci.yml (consumer)
jobs:
  build:
    runs-on: [self-hosted, linux, arm64, microvm]
    timeout-minutes: 60
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - run: make build
