Proposal · v0.1

Ephemeral GitHub runners on
AWS Lambda MicroVMs

Each repository deploys its own runners into its own AWS account with Terraform. Every job gets a fresh Firecracker VM, runs for at most one hour, can read only that repository's secrets, and is then destroyed.

01 · Design reviewWhat changes with "runners only, 1 h max"

The first draft had an org-level router and a cross-account hop. With only runners to build and a 1-hour cap, the router is not worth it. Each repository gets a small, self-contained stack in its target account.

Keep: Lambda MicroVMs

A fresh VM per job, per-second billing and no idle cost. One hour is well inside the 8-hour MicroVM limit.

Keep: JIT runners + GitHub App

A single-use registration per job. The App key stays in the dispatcher and never enters a VM.

Drop: org router & cross-account role

No shared control plane and one less trust boundary. The webhook goes straight to the repo's own account.

Drop: suspend / resume / warm pool

No idle policy and no snapshot state between jobs. Run, then terminate.

Drop: EC2 & capacity providers

Capacity providers are for Lambda Managed Instances, not MicroVMs. EC2 adds idle cost and AMI work you don't need at this scale.

Watch: arm64 only

Every action, container and binary must have an arm64 build. Keep ubuntu-latest for x86-only jobs.

The 1-hour cap is enforced in three places

LayerSettingEffect
Workflowtimeout-minutes: 60GitHub cancels the job. This is the clean stop.
MicroVMmaximumDurationInSeconds = 3900Lambda hard-kills the VM at 65 min (60 min job + 5 min boot margin).
Sweeperevery 5 minTerminates any VM older than 65 min and re-queues orphaned jobs.

02 · ArchitectureOne stack per repository

Everything sits in the target account. Idle cost is close to zero: two Lambdas, one queue, one table and two secrets.

Components

ComponentServiceWhy
Webhook receiverLambda Function URL (Go)Checks the HMAC, keeps only queued/completed events with matching labels, and enqueues them. No API Gateway needed.
QueueSQS + DLQRetries when RunMicrovm is throttled. Failed jobs land in the DLQ, not nowhere.
DispatcherLambda (Go), batch size 1Deduplicates jobs, mints the JIT config, launches or terminates VMs, and caps concurrency.
StateDynamoDB (on-demand, TTL)Maps job_id → microvm_id. A conditional put blocks duplicate launches.
SweeperEventBridge Scheduler → LambdaReaps VMs older than 65 min and re-dispatches jobs whose webhook was lost.
Runner imageawscc_lambda_microvm_imageBuilt from a Dockerfile plus a zip in S3. Contains actions/runner (arm64), Docker and a small supervisor.

03 · Job lifecycleFrom queued to terminated

The runner never sees the GitHub App key. It receives a pointer to a one-time SSM parameter, reads it, deletes it and runs exactly one job.

Edge cases handled

CaseHandling
Duplicate webhook deliveryA DynamoDB conditional put on workflow_job.id drops the second launch.
Runner picks up a different job (same labels)Fine. The dispatcher maps the VM by runner name (mvm-<job_id>) on completed, and the sweeper launches a runner for any job left queued.
Lost webhookThe sweeper lists queued jobs for the repo and dispatches any that are missing.
RunMicrovm throttledThe message goes back to SQS with backoff, then to the DLQ after 5 attempts. An alarm fires on DLQ depth.
Job hangs past 60 minGitHub cancels it. Lambda kills the VM at 65 min.

Decision · ADR-001Terminate after every job — no VM reuse

Keeping a finished VM idle so the next job starts faster saves little time and breaks the guarantee that every job gets a clean VM.

OptionStart timeIsolationIdle costVerdict
Reuse a running VMFastest✗ inherits previous job's disk, Docker cache and processesFull compute (~$0.25/h at 2 vCPU / 4 GB)Rejected
Suspend after the job, resume for the next oneFast✗ same dirty stateSnapshot storage, counts against the memory quotaRejected
Fresh VM per job, terminate afterSnapshot start + runner registration✓ clean VM every timeNoneChosen
Warm pool of clean VMs (suspended before registering)Slightly faster✓ still one job per VMSnapshot storage, uses memory quotaOnly if M1 shows a real gap

Why the gain is small

RunMicrovm already starts from a memory snapshot, not a cold boot. Most of the remaining delay is runner registration and GitHub assigning the job, and reuse removes neither.

JIT runners are single-use

A reused VM would still need a new JIT config per job, delivered on resume. That means more state for little benefit.

Make starts faster instead

Bake the unpacked runner, toolchains and common actions and images into the snapshot. Start dockerd only when a job uses it.

Measure first

M1 records the time from queued to in_progress. Add the warm pool only if that number is too high.

04 · Secrets & trustEach repo sees only its own secrets

Three IAM roles, each with one job. The runner role is scoped to the repo's prefix, so repo-a cannot read repo-b secrets even in the same account.

Private repos only

GitHub advises against self-hosted runners on public repositories. If you need one, set "Require approval for all external contributors".

Labels are not security

Anyone who can edit a workflow can request the label. The repo boundary and prefix-scoped IAM are what isolate jobs.

App key never in state

Create the Secrets Manager value out of band. Terraform receives only the secret ARN.

Egress

Default: INTERNET_EGRESS. Optional: a VPC_EGRESS connector with NAT and a DNS firewall allowlist.

06 · UsageHow a repository onboards

  1. Once per account: apply modules/bootstrap. It creates the GitHub OIDC provider and a deploy role per repo. Store the GitHub App key in Secrets Manager.
  2. Install the GitHub App on the repo with Administration: write and subscribe it to Workflow jobs events.
  3. In the repo, add infra/runners/main.tf calling repo-runner, and a runners Environment with required reviewers.
  4. Deploy from a GitHub-hosted runner, so the runners don't have to deploy themselves.
  5. Point the webhook at webhook_url, then use the labels in workflows.
# .github/workflows/deploy-runners.yml
on: { push: { branches: [main], paths: ["infra/runners/**"] }, workflow_dispatch: {} }
permissions: { id-token: write, contents: read }
jobs:
  apply:
    runs-on: ubuntu-latest
    environment: runners
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: ${{ vars.RUNNERS_DEPLOY_ROLE_ARN }}, aws-region: eu-west-1 }
      - uses: hashicorp/setup-terraform@v3
      - run: terraform -chdir=infra/runners init && terraform -chdir=infra/runners apply -auto-approve
# .github/workflows/ci.yml
jobs:
  build:
    runs-on: [self-hosted, microvm]
    timeout-minutes: 60
    steps:
      - uses: actions/checkout@v4
      - run: |
          TOKEN=$(aws secretsmanager get-secret-value \
            --secret-id gha/my-org/my-repo/npm-token --query SecretString --output text)
          make build
